## Vision (verbatim)

Data storage Either a real database (MongoDB or PostgreSQL) or an in-memory/simulated store (e.g., an in-memory array or a JSON file).

If you use an in-memory store, its data-access functions must still be asynchronous (return Promises / use async/await), the way a real database driver would be.

The body must include title, a non-empty string.

Suggested task shape (you may add fields): { "id": "a1b2c3", "title": "Write the README", "createdAt": "2026-11-02T09:30:00Z" }

Unit tests must mock the data-access layer and focus on business logic.

Testing Jest, with at least 80% code coverage.

Validation errors Reject invalid requests with 400 Bad Request and a clear error message.

## Cross-package effects

- **The in-memory adapter is `apps/api`'s, and it must satisfy §2 there.** This spec asserts only
  that the core AWAITS the port (S3); that the adapter's own `list`/`add` return Promises is a
  promise `@cheq/core` cannot keep, because the adapter is not in it (probe decision 1: an adapter
  inside the core would let a core test reach the real store instead of a mock, and the coverage
  figure would then describe the adapter rather than the logic). CHQ-002 implements that side.
- **The `400` of §7 and §3 is `apps/api`'s.** The core returns a named failure; mapping it to a
  status code and a response body is CHQ-002's.
- **The id and the instant are supplied by `apps/api`.** Forced, not chosen: `L-core-purity`'s token
  scan forbids `Math.random(`, `Date.now(`, `performance.now(` and `new Date()` under
  `packages/core`, so neither can originate here. CHQ-002 owns both sources.
- **Uptime is not the core's.** It belongs to the process, which is why the probe record kept
  `HealthSnapshot` out of this package. `GET /health` is CHQ-002 entirely.
- **CHQ-002 owns the id SOURCE and asserts it there.** The core validates nothing about an `id`
  (Q2), so "every created task gets a distinct id" is a promise `@cheq/core` cannot keep: it never
  sees two calls. That assertion belongs to whichever code generates ids.
- **CHQ-002 asserts that its in-memory adapter returns insertion order** (Q3). The core guarantees
  no order, so if the API is to promise one, the promise is tested where the order is produced. The
  README states that the API contract itself guarantees none.

## Non-goals

- Update, delete, completion, assignment, due dates, priorities, ordering rules and pagination. The
  assignment's endpoints are `GET /health`, `GET /tasks` and `POST /tasks`; none of those behaviours
  is named anywhere in it, and inventing one would be inventing a requirement.
- Durable storage of any kind, and any choice between MongoDB and PostgreSQL. §1 leaves that open
  and this package cannot hold either (Premise check).
- A generic `Result<T, E>` with `Ok`/`Err` helpers. Exactly one failure mode exists; probe decision
  6 chose a named union over machinery for a single case, and this is where that choice is recorded
  rather than re-made later.
- Branded `TaskId` / `createdAt` types. Probe decision 3: the values cross a JSON boundary in both
  directions, and branding charges a cast at every crossing. Rejected, not unconsidered.
- An error type for a duplicate id. The id source is ours and produces one per call, so a collision
  would be a bug in that source; an error type for it now would be inventing a requirement.
- Any rule about the `id`'s FORMAT, and any validation of it at all (Q2). `"a1b2c3"` is an example
  inside a "suggested" shape, and the core accepts whatever string it is handed.
- Any order guarantee from the core (Q3). It returns the order the port resolved with.

## Answered questions

- Q1: Is a title of whitespace only — `"   "` — a "non-empty string" (§5), and if it is rejected, is
  the STORED title the trimmed one or the one that was sent? → **reject after trimming, and store the
  trimmed title** (Sam, 2026-11-02): CHQ-003 is required by the assignment to validate the title on
  the client ("the title is required"), so a backend that accepted `"   "` would put the two layers
  in disagreement; and "a clear error message" (§9) loses its purpose if the API accepts a task
  nobody can read. Storing the trimmed value is the second half of one decision rather than a second
  behaviour: trimming only for the check would let `"  Write the README  "` through with its padding
  intact, so the list would render the padding and two tasks with the same visible title would be
  indistinguishable. Trimming once, where the title is validated, is one rule. It adds no failure
  mode — `"   "` trims to `""` and hits the same single failure — so probe decision 6 (a named union
  for one case, not a generic `Result`) still holds. **This is an interpretation, not a requirement
  the assignment states**, and it is recorded as one under Contradictions below. Asked at all because
  the rule against inventing requirements is this project's; the answer was the standard one, and a
  gap convention settles is better decided with its reason written down than turned into a question.
- Q2: Who supplies the task `id`, and is its format a requirement? → **`apps/api` supplies it, and
  the format is NOT a requirement; the core passes it through and validates nothing about it** (Sam,
  2026-11-02): §6 is a "Suggested task shape (you may add fields)", and "suggested" governs the whole
  shape — asserting six base36 characters would be inventing a requirement, and a weak one. Refusing
  an EMPTY id was considered and rejected: it would add a second failure mode to the core, and probe
  decision 6 rests on there being exactly one. Generation belongs to the ticket that owns the id
  source and is asserted there. S7 carries the core's side: pass-through, unchanged.
- Q3: Does `GET /tasks` have an order requirement? → **the core guarantees none; CHQ-002 asserts
  insertion order as the ADAPTER's behaviour** (Sam, 2026-11-02): the assignment says only "200 with
  a JSON array of tasks ([] when there are none)", so an order imposed in the core would be invented.
  But an in-memory array returns insertion order as a side effect of how it is written, and a reader
  may take that for a promise — so the promise is made explicitly where it is produced, with its own
  assertion in CHQ-002, and the README states that the API contract guarantees no order. S4 is
  unchanged: the core returns the order the port resolved with and reorders nothing.

- S1–S5 all assume a task model, a store port and a create/list use case in `@cheq/core`. Today that
  package exports one marker constant (`packages/core/src/index.ts:8`) and nothing else. Closing
  that gap IS this spec; it is recorded here so the test phase's red is understood as the designed
  state rather than as a broken premise.
- §6 asks for backend coverage at or above 80%, and the floor is declared in `jest.config.mjs` while
  no lane reads it (TD-0013, measured 2026-11-02). Measured on the skeleton the branch figure is
  below the floor (72.54%) for code that is pipeline support rather than product, so the number
  currently describes the wrong denominator. Not closed here, and not closed by narrowing the
  denominator either — that would be turning a floor green by narrowing an include.
- §1's two branches are not a choice this package can make at all (Premise check). The spec records
  the fork as collapsed rather than as decided, which is a stronger statement than picking a side
  and is the one thing the storage probe actually established.
- **Trimming the title is this spec's interpretation, not the assignment's words.** §5 says
  `non-empty` and nothing about whitespace; S1 rejects `"   "` and S6 stores the trimmed value
  because of the reasoning in Q1, not because the assignment asked. It is written here so a reviewer
  can disagree with the reason rather than discover the behaviour. The weaker half is S6: rejecting
  `"   "` is conventional, whereas rewriting a title the caller sent is a transformation, and if it
  is unwanted the cure is to withdraw S6 and leave S1 as it stands.

## Appendix: implementation notes (not part of the contract)

**The test phase must not read this section.**

Shape as the probe record decided it ([CHQ-001.probe-storage.md](CHQ-001.probe-storage.md), six
numbered decisions with their reasons):

- `packages/core/src/tasks/` (decision 2 — it matches the route it serves).
- `Task = { id: string; title: string; createdAt: string }` — plain strings, not branded
  (decision 3).
- The port as METHODS, `{ list(): Promise<Task[]>; add(t: Task): Promise<Task> }` (decision 5 —
  `list` is the word the route uses, and a mock of a method reads like the thing it replaces).
- Time as a VALUE in the use case's arguments, not a `Clock` interface (decision 4).
- Failure as a small named union specific to the one case, not a generic `Result` (decision 6).
- The in-memory adapter lives in `apps/api`, never here (decision 1).

The contracts the test phase may add under `packages/core/src/contracts/CHQ-001/` are exactly those
types: the task, the port, the failure union. No function body, and nothing that answers Q1, Q2 or
Q3 — an open question must not be settled by a type.
