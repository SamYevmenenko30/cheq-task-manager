# CHQ-001 · probe: the storage fork — the disagreement record

Machine-written evidence, not an argument made afterwards. Three independent
attempts answered one question with no channel between them; a reducer in plain
code compared the shapes they declared. What follows is what they agreed on, what
they disagreed about, and which way each disagreement was decided — with the
reason, so a reader can disagree with the reason rather than guess at it.

**The question**, in the assignment's own words:

> Data storage Either a real database (MongoDB or PostgreSQL) or an
> in-memory/simulated store (e.g., an in-memory array or a JSON file). If you use
> an in-memory store, its data-access functions must still be asynchronous
> (return Promises / use async/await), the way a real database driver would be.

**The attempts:** three, one per model tier of one vendor — opus, sonnet, haiku.
Each was given the repository and its rules, asked for the SHAPE only (file paths
and full export signatures, no implementation, no tests), and told the others were
running. Declared limit: **within-vendor**. This measures disagreement between
tiers of one lineage, not between independent ones, and nothing here claims
otherwise.

## What they agreed on

All three chose **in-memory** — but the agreement is less interesting than the
reason the strongest attempt gave, which reframes the fork:

> `packages/core` cannot hold a driver at all — `dependencies: {}`,
> `node-linker=isolated`, no `DOM` in `lib`, no ambient types, so `node:net` is
> TS2591 and a Mongo/Postgres client cannot even resolve — which means the store
> is a port with an injected adapter in **either** branch of the fork.

So inside the core the fork does not exist. Both branches collapse to the same
shape: a port, and an adapter injected from outside. The fork is real only in the
adapter layer, and there it is a question about deployment and durability rather
than about the domain. A second attempt reached the same conclusion independently.

That is the finding. It was not in the question, and an argument that started from
"which store should we use" would have answered a narrower question than the one
that mattered.

## What they disagreed about, and how each was decided

The reducer found exactly ONE file all three declared — `packages/core/src/index.ts`
— and **not one export with the same signature across all three**. The assignment
fixes the shape on the wire (`{ id, title, createdAt }`) and decides nothing about
the surface behind it. Six decisions follow, each ours to make:

| # | the disagreement | decided | why |
|---|---|---|---|
| 1 | where the in-memory adapter lives: inside `packages/core` (two attempts) or in `apps/api` (one) | **`apps/api`** | the assignment asks that unit tests "mock the data-access layer and focus on business logic". With a real adapter sitting inside the core, a core test can reach for it instead of a mock, and the coverage figure then describes the adapter rather than the logic. Outside, the mock is the only way in. |
| 2 | directory: `src/task/` or `src/tasks/` | **`src/tasks/`** | two of three, and it matches the route it serves (`/tasks`). Cosmetic, decided once so it stops being decided again. |
| 3 | `TaskId` and `createdAt`: branded (`string & { __brand }`) or plain `string` | **plain `string`** | the values cross a JSON boundary in both directions. Branding buys safety inside the core and charges a cast at every crossing; for three endpoints that is ceremony a reviewer is right to ask about. Rejected, not unconsidered. |
| 4 | time: `interface Clock { now(): Date }`, `type Clock = () => Date`, or `now: Date` passed as a VALUE | **a value** | the core may not call `new Date()` with no arguments at all (L-core-purity level 3), so time enters either way. A value makes the use case trivially deterministic — the test passes an instant, not a fake clock — and `list` needs no clock at all. |
| 5 | the port: `{ list, add }` as readonly arrow properties, or `{ findAll(), add() }` as methods | **`{ list(), add() }`, methods** | `findAll` is ORM vocabulary for something that is not an ORM; `list` is the word the route uses. Methods because a mock of a method reads like the thing it replaces. |
| 6 | failure: a generic `Result<T, E>` with `Ok`/`Err` helpers, or a small union specific to the case | **a specific union** | exactly one failure mode exists — a title that is not a non-empty string. A generic Result plus two helper types is machinery for a single case, and the assignment asks for "a clear error message", which a named union carries better than `E`. |

Two more, raised by one attempt each and worth recording as not-now rather than
not-considered: a `HealthSnapshot` type in the core (the uptime belongs to the
process, not the domain — it stays in `apps/api`), and a `DuplicateTaskIdError`
(the id source is ours and generates one id per call; a collision would be a bug
in the id source, and inventing an error type for it now would be inventing a
requirement).

## What this probe did NOT do

No twin, no null model, no convergence claim, no merge of the attempts' code. The
attempts wrote nothing: they returned shapes, and the comparison is over declared
shapes rather than over diffs. Convergence is not reported at all — the signal
taken here is DISAGREEMENT, because that is what answers "what did the assignment
leave open", and the one recorded run of the original method measured convergence
at 0 of 2 and concluded it had measured the scaffolder.
