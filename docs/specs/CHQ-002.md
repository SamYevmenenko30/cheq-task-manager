## Vision (verbatim)

Framework Express, Fastify, or NestJS.

If you use an in-memory store, its data-access functions must still be asynchronous (return Promises / use async/await), the way a real database driver would be.

Middleware Implement a custom request-logging middleware that logs every incoming request (e.g., method, path, status code, and response time), plus basic request validation.

Validation errors Reject invalid requests with 400 Bad Request and a clear error message.

GET /health Report service health for load balancers and monitoring 200 with the service status and uptime, e.g. { "status": "ok", "uptime": 1234 }

GET /tasks List all tasks 200 with a JSON array of tasks ([] when there are none)

POST /tasks Create a task The body must include title, a non-empty string.

Success: 201 with the created task.

Invalid body: 400 with an error message.

All three endpoints behave as described, including the 400 case.

Every request produces a log line from your middleware.

- **`@cheq/core` owns the title rule and this package may not restate it.** S5 and S8 must reach

- **The id and the instant are this package's**, as CHQ-001's `## Cross-package effects` states:
  the core may not call `Math.random(`, `Date.now(`, `new Date()` or `performance.now(`

  non-empty and distinct per request, which is the promise CHQ-001's Q2 deferred to here.
- **Insertion order is this package's**, as CHQ-001's Q3 decided: the core returns the order the
  port resolved with and promises none, so S3 is where an order is promised at all. CHQ-007's README
  states that the API contract itself guarantees no order.
- **Nothing in `apps/web` is asserted here.** The frontend consumes these endpoints and is CHQ-003.

- An OpenAPI document, a versioned path prefix, CORS configuration. None is named in the

  there with its own reason rather than being guessed at here.
- A health check that reports anything about the STORE (Q2). §7 asks for the service's status and

- A log line's human readability. The entry is JSON for an aggregator (Q1); a developer reading it in

## Answered questions

- Q1: Where does the log line go, and in what form? → **one JSON object per line to stdout, with the
  sink INJECTED into the app factory** (Sam, 2026-11-02). Fastify's own logger stream was already out
  by §3's "custom". Between JSON and a human-readable line the consequences differ, which is why this
  was asked: stdout is collected by the container (CHQ-004) and by CloudWatch (CHQ-005), and JSON is
  parsed there without a grok pattern, so the fields stay queryable. A formatted string needs a
  parser in the one place nobody will write one. §3's four fields are introduced by `e.g.` and are
  therefore a FLOOR: the entry also carries `time` (ISO-8601, so a line is usable once it reaches an
  aggregator), `level` (chosen from the outcome) and `requestId` (so lines about one request join) —
  and never the request body, which is user data. S6, S9 and S10 carry those three additions.
  **The second half of the answer matters as much as the first:** the factory takes `log` as an
  argument, defaulting to stdout, so a test passes a collector and asserts over an array. A test that
  patches `process.stdout` tests the patch rather than the middleware, and breaks whenever anything
  else in the process writes a line.
- Q2: Does `GET /health` report anything the process does not already know? → **no, it does not touch
  the store — and that is now an assertion rather than a paragraph** (Sam, 2026-11-02). An in-memory
  store is an array in the same process and cannot be unavailable, so "checking" it would be theatre:
  always green, while suggesting the endpoint verifies a dependency. When a real database arrives, a
  dependency check earns its place and comes with its own assertion. The decision has a stronger
  form, and it is the one taken: health must answer 200 EVEN IF the store is broken (S11), because a
  load balancer routes on it and a health check that fails with the business path takes a live
  instance out of rotation for a reason it cannot fix. That is falsifiable, where "we decided not to
  check" is not.

## Contradictions with the project as it stands

- **"Custom" rules out Fastify's built-in logger, and that is a decision.** Fastify ships `pino` and
  `app.log` would produce a line per request with less code. §3 asks for "a custom request-logging
  middleware", so using the framework's own logger answers a different question than the one asked —
  and the assignment is a hiring exercise where the middleware IS the thing being examined. So S6
  asserts a hook this repository wrote. The cost is recorded here: a hand-written line is one more
  thing to maintain than a configured logger, and in a product that was not an exercise the built-in
  one would be the better answer.
- **S5 asserts `{"title":"   "}` is 400, which rests on CHQ-001's interpretation and not on the
  assignment's words.** §11 says `non-empty` and nothing about trimming; CHQ-001 read it as
  non-empty-after-trim with the reason recorded there, and this ticket inherits that. If that
  interpretation is withdrawn, S5's whitespace case and S8 both change.
- **S1 asserts `uptime` does not decrease, which is more than §9's shape.** A literal reading is
  satisfied by `{"status":"ok","uptime":1234}` hard-coded, and that would pass a shape check while
  telling a load balancer nothing. The stronger assertion is deliberate and is the kind of thing the
  Done-when "behave as described" is for.
- **There is no coverage lane yet, and this ticket's Done-when needs one.** TD-0013 measured that
  the floor is declared and read by nothing; the `L-coverage` row above is new in this spec and
  lands `soft`, because its denominator today is pipeline support rather than product code. Making
  it `hard` is a decision for the commit that can show the figure over the product.

## Appendix: implementation notes (not part of the contract)

**The test phase must not read this section.**

- `apps/api/src/` gains the app factory, the store adapter and the logging hook. The factory takes
  its dependencies as arguments — the store, the id source, the clock — so a test builds an app
  whose store is a mock and whose ids are predictable, which is what §"unit tests must mock the
  data-access layer" asks for and what makes S4's "two different ids" assertable without luck.
- The adapter is an array behind `{ list(), add() }` returning Promises, satisfying S7 at the port.
- `process.uptime()` for S1 and `crypto.randomUUID()` for the id: both `node:` surfaces this
  package may use and the core may not. The id's FORMAT is not a requirement (CHQ-001's Q2), so a
  uuid is chosen for being collision-free without a dependency rather than for matching the
  assignment's six-character example.
- The logging hook goes on Fastify's `onResponse`, which is where the status code and the elapsed
  time are both available; `onRequest` would have the method and path and neither of the other two.
  The exact hook name is cited from `docs/vendor/fastify.md` at implementation time, not from memory.
- The `log` sink is a factory argument defaulting to a stdout writer, per Q1; `requestId` comes from
  `crypto.randomUUID()` like the task id, on the same `node:` surface. The hook that emits the entry
  stays on `onResponse`, where the status and the elapsed time are both available.
- S11 is satisfied by the health route reading nothing but `process.uptime()`, which is also why it
  is the one route that takes no store argument at all.
