## Vision (verbatim)

Step 2 – Frontend (React) 
Build a clean, responsive single-page web application that consumes your API endpoints. 
Requirements 
Area Requirement 
Framework / build 
tool 
React, built with Vite or Next.js (Create React App is also accepted). 
Task list Fetch and display all tasks from GET /tasks. 
Create-task form Add a task via POST /tasks, with client-side validation (the title is 
required and can’t be empty). 
UI states Handle loading, empty (no tasks yet), and error states gracefully, e.g., 
show an alert when an API call fails. 
Health indicator Display a visual indicator in the UI of the API’s health, based on GET 
/health (e.g., a green/red badge). 
Code structure Separate components cleanly. Put API calls in custom hooks or a state-
management layer. Use standard styling (CSS Modules, Tailwind, or 
styled-components). 
Testing The 80% coverage requirement applies to the backend. Frontend tests 
are welcome but not required. 
 
Done when 
• A user can view tasks, add a task, and see it appear in the list. 
• Invalid input is caught in the form before it reaches the API. 
• When the API is down, the app shows an error state and the health indicator shows the 
API as down. 
• The layout works at both desktop and mobile widths.

## Cross-package effects

- **CHQ-005 already depends on an artifact this ticket must produce.** `infra/` syncs the Vite build
  output into the SPA bucket, and `apps/web/package.json:11` is `"scripts": {}` — there is no build
  script and `vite build` has never run here (TD-0010). The constraint: this ticket owes a build whose
  output is a static directory servable from S3 with no server-side rendering, because the
  infrastructure has one origin for static files and one for the API and nothing in between. Adding a
  `build` script is not a dependency change, so the implementation phase may do it; **no lane verifies
  that the build succeeds**, and that gap is TD-0010's, not this spec's to close.
- **The SPA must call the API with RELATIVE paths.** CloudFront serves both halves from one origin
  (`infra/cdn.tf`), so `/tasks` and `/health` resolve without a base URL. An absolute URL baked at
  build time would couple the frontend build to a Terraform output and break the same-origin property
  the infrastructure was chosen for. Enforced by nobody today: no light reads the SPA's fetch calls.
- **Local development needs a dev proxy** for the same reason: with relative paths, `vite dev` must
  forward `/tasks` and `/health` to a local `@cheq/api`. That is `apps/web/vite.config.ts`, which
  exists, and the change is this ticket's.

## Non-goals

- Editing, completing or deleting a task. The API has no route for any of them (`project.mjs routes`:
  three registrations), so the SPA cannot do what the server does not offer.
- Client-side routing. Decided below; it is also what keeps `infra/cdn.tf`'s decision to carry no
  distribution-wide `custom_error_response` correct.
- Authentication, pagination, filtering, sorting, optimistic updates and offline behaviour. The vision
  names none of them.
- A design system or a component library. §7 offers three styling options and all three are styling.

## Contradictions with the project as it stands

- **§7's fork, decided: custom hooks, not a state-management layer.** The vision offers either. The
  SPA has one resource and three operations over it, and a store would add a layer with no second
  consumer. The decisive reason is mechanical rather than aesthetic: a state library is a new runtime
  dependency, `L-deps` requires a `package:` line at column zero plus a vendor digest for one, and
  the implementation phase may not add dependencies on its own — so a store is a question for the
  human while hooks need nothing new. Recorded as the loser: a store would pay off the moment a second
  screen reads the same tasks, and there is no second screen.
- **§7's styling, decided: CSS Modules.** Of the three the vision names, Vite supports CSS Modules
  with no dependency at all, while Tailwind and styled-components each add one — the same `L-deps`
  reason as above. Recorded as the loser: Tailwind would make S11's two widths quicker to write.
- **The web will name `@cheq/core`'s `Task` type, decided.** `apps/web/package.json:7` declares the
  dependency and `L-graph` reports that nothing imports it. Importing the type means the shape the API
  returns and the shape the SPA renders are ONE declaration; declaring a second `Task` interface in
  the SPA would be two shapes that can disagree with nothing noticing. This also gives that declared
  dependency its first caller.
- **No client-side routes, decided.** One page, one view. `infra/cdn.tf` states the consequence it
  depends on: a distribution-wide `custom_error_response` mapping `404 → /index.html 200` would
  rewrite a genuine API `404` into an HTML page with status `200`, so the SPA fallback is deliberately
  absent and the day CHQ-003 wants routes it needs a CloudFront Function scoped to the SPA behaviour.
  Recorded as the loser: a route per task would give a shareable link to one task.
- **S6, decided: the created task is read from the `201` body, not refetched.** `POST /tasks` returns
  the created task (CHQ-002 S4), so a refetch would be a second round trip to learn what the server
  just said, and it would make "see it appear in the list" depend on two requests instead of one.
  Recorded as the loser: a refetch would also pick up tasks another client created.
- **§8 contradicts this project's method, and the method wins.** The assignment says "Frontend tests
  are welcome but not required". `docs/specs/BACKLOG.md:44` puts CHQ-003 through all three phases, so
  ten of these eleven assertions get a test that `red-check` proves red on the base before any
  implementation exists. The contradiction is deliberate and is recorded rather than resolved: the
  assignment sets a floor, not a ceiling, and a reviewer asking "why did you test what you did not
  have to" has the answer here.
- **S11 contradicts the pre-flight, and nothing resolves it in this ticket.** The vision's §12 is a
  pixel fact; `BROWSER_PROBE=absent`, so it gets no test. The spec asserts it anyway so the day the
  probe passes the sentence is already written and falsifiable.
