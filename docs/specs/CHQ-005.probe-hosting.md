# CHQ-005 · probe: the hosting fork — the disagreement record

Machine-written evidence, not an argument made afterwards. Three independent
attempts answered one question with no channel between them; what follows is what
they agreed on, what they disagreed about, and which way each disagreement was
decided — with the reason, so a reader can disagree with the reason rather than
guess at it.

**The question**, in the assignment's own words:

> Default option: an EC2 instance that runs your container … Alternative: if you
> find a simpler way to host the backend and frontend on AWS (e.g., ECS on
> Fargate, App Runner, or S3 + CloudFront for the frontend), go for it.

**The attempts:** three, one per model tier of one vendor — opus, sonnet, haiku.
Each was given the repository, the container that already exists, and the
assignment's words; each was asked for the SHAPE only (file paths, resource list,
variables and outputs, no HCL) and told the others were running. Declared limit:
**within-vendor**, the same limit as [the storage probe](CHQ-001.probe-storage.md).
This measures disagreement between tiers of one lineage, not between independent
ones, and nothing here claims otherwise.

Each attempt was also told, marked as a risk factor rather than a filter, that the
account's organization currently denies `apprunner`, `ecr`, `ecs`, `lambda`, `ec2`,
`cloudformation`, `lightsail` and `amplify` by service control policy, and allows
`s3`, `iam`, `sts` and `elasticbeanstalk`. Marked that way on purpose: stated as a
filter it would have produced agreement about a transient account problem, and
agreement bought that way measures nothing.

## The fact that decided it, which the probe is the reason anybody looked up

**AWS App Runner is closed to new customers.** One attempt had its first pick
overturned by this and said so; a second reached it independently; the third
proposed App Runner as its answer, not knowing. Verified here against the vendor's
own documentation rather than taken from any attempt:

> AWS App Runner is no longer open to new customers. Existing customers can
> continue to use the service as normal. […] we do not plan to introduce new
> features.
> — <https://docs.aws.amazon.com/apprunner/latest/dg/apprunner-availability-change.html>

Effective 2026-04-30. New accounts, and existing accounts that never used the
service, cannot create App Runner services. The account for this work was created
on 2026-11-01, so **App Runner is unavailable here no matter what happens to the
service control policies**, and the shape that two sessions of this project had
been assuming — ECR plus App Runner — was dead before it was written.

That is the finding. It was not in the question, two of three attempts would have
answered it correctly, and an argument conducted without the probe would have
produced the one shape that cannot be built.

Also verified here, because one attempt's reason rested on it: the Terraform AWS
provider **does** cover AWS's named successor —
`aws_ecs_express_gateway_service`, added in provider 6.23. One attempt dismissed
ECS Express Mode for leaving load-balancer and certificate resources behind on
`destroy` (attributed to community reports, UNVERIFIED here) and another recorded
its Terraform coverage as unknown; coverage exists, and the open gap is a missing
`cpu_architecture` argument, so a service created by Terraform runs x86_64
(<https://github.com/hashicorp/terraform-provider-aws/issues/50361>).

## What they agreed on

All three chose the same SHAPE for everything except the compute, and the
agreement is more useful than any one of the answers:

1. **One CloudFront distribution in front of both halves.** The SPA is a private
   S3 bucket reachable only through an origin access control; `/health` and
   `/tasks` are ordered cache behaviours pointing at the API origin with caching
   disabled. The browser therefore sees ONE origin.
2. **Which deletes three problems at once**, and all three said so: no CORS layer
   in `apps/api` (deferred by CHQ-002 and still deferred), no API base URL baked
   into the Vite build — which would couple the frontend build to a Terraform
   output — and no mixed content when the backend origin speaks plain HTTP.
3. **GitHub OIDC for CI**, `sts:AssumeRoleWithWebIdentity` with the trust policy
   pinned to this repository and `refs/heads/main`. No long-lived access key
   exists anywhere; the only thing stored in the repository is a role ARN.
4. **The CloudFront-to-backend leg is plain HTTP**, and every attempt named it as
   the cost of the arrangement rather than leaving it implicit.
5. **The in-memory store is wiped by every deploy** and by any instance
   replacement. Named by all three; two added that the README has to say it.

The shared shape is not a compromise between the three — each reached it from its
own compute choice, which is why it is recorded as the finding rather than as a
preference.

## What they disagreed about, and how each was decided

### 1. The compute. App Runner · EC2 single instance · Elastic Beanstalk

Decided: **ECS Express Mode**, AWS's named successor to the service all three
attempts reached for.

This decision was taken twice. It first read "a single EC2 instance", on three
grounds — that the in-memory store wants exactly one process, that `t3.micro` is
inside the twelve month free tier while Fargate and its load balancer are not, and
that EC2 is the assignment's own default and so needs no defence. It was then
re-opened on being asked which way was actually SIMPLEST, and two of those three
grounds did not survive the question:

- **The cost argument was sized for the wrong lifetime.** The free tier matters
  across a year. This stack lives two or three weeks and is then destroyed. Express
  Mode at `cpu = 256` / `memory = 512` is roughly $9/month of Fargate plus about
  $16/month of load balancer — **$12 to $18 for the whole life of the exercise.**
  (Its DEFAULTS are 1 vCPU and 2 GB, four times what one Node process needs and
  about $36/month of Fargate alone, which is why `infra/api.tf` sets both.)
- **The HTTPS leg.** Express Mode terminates TLS on its own load balancer with a
  certificate it manages, and publishes `https://<service>.ecs.<region>.on.aws/`.
  That removes the one cost EVERY attempt recorded against its own shape: the
  CloudFront-to-origin hop is HTTPS rather than plain HTTP, with no certificate and
  no domain of ours.
- **What stayed true**: the store is one process's RAM. It is served by pinning
  `scaling_target` to 1..1 rather than by the platform, and the caveat below is the
  part no platform can remove.

And the simplicity the assignment invites is measurable, not a matter of taste.
The EC2 shape needs about seven resources of its own — an AMI lookup, the instance,
a security group scoped to CloudFront's prefix list, a role, an instance profile,
two policy attachments — plus a shell script inside Terraform to install Docker and
a deploy channel (an SSM document, a `send-command`, a wait) and `ignore_changes =
[ami]` so an AMI refresh does not silently replace the box. Express Mode needs ONE
resource and two roles, and a deploy is `-var image_tag=<sha>`.

Recorded against it, because the trade is real: that one resource creates roughly
ten in the account — load balancer, listener, target group, security groups,
auto-scaling target and policy, log group, alarm, certificate — and NONE of them is
in Terraform's state. A console reader sees resources this repository cannot
account for, which is the opposite of what "nothing created by hand" is usually
taken to mean, and `terraform destroy` is reported to leave the load balancer and
certificate behind (UNVERIFIED, TD-0019). The EC2 shape's parts are ours to own;
Express Mode's are AWS's to own, and that is a choice about who is responsible, not
about how much exists.

Elastic Beanstalk was rejected for a different reason: it is `elasticbeanstalk`
plus, underneath, EC2, auto scaling and load balancing called with the CALLER's own
permissions, so it inherits every EC2 denial while adding a platform-branch
lifecycle to track. The attempt that proposed it identified exactly this as its
least-sure point.

### 2. The registry. ECR · GitHub Container Registry

Decided: **ECR.** The GHCR proposal was the only shape that could have pushed an
image before the policies are lifted, and it buys nothing, because the image was
never the blocker — the compute is, and no compute option survives today's denials
either. Against that, GHCR puts a dependency outside the account the assignment
asks to see described in Terraform.

### 3. Terraform state. Local · an S3 backend behind a `bootstrap/` stage

Decided: **the split**, as two of three proposed, both for the same reason: the
OIDC provider, the deploy role and the registry must exist BEFORE the first CI run
can push anything, and a single root cannot create the identity that applies it.
`bootstrap/` keeps local state, is applied once by hand, and creates the state
bucket that the application root then uses.

### 4. Does CI run `terraform apply`?

Decided: **yes**, with the image tag as the only per-deploy input. The dissenting
shape kept Terraform out of the workflow so the CI role could stay narrow, which
is a real security argument — but the ticket asks for deployment with no manual
step, and a workflow that cannot change infrastructure cannot deliver a change to
it. The narrowness is recovered by `bootstrap/` NOT being in CI's reach: the
identity and the registry are applied by hand, and the role CI assumes cannot
rewrite them.

### 5. The SPA fallback, where two of three carried a defect

Decided: **no distribution-wide `custom_error_response`**, as the one dissenting
attempt argued. The other two mapped `403/404 → /index.html 200` for client-side
routing. CloudFront custom error responses are configured per DISTRIBUTION, not
per behaviour, so that mapping rewrites a genuine `404` from the API origin into an
HTML page with status `200` — an API client would see a successful response
containing the SPA. Two of three shapes shipped that; the third named the
mechanism and left the fallback out.

CHQ-003 therefore either has no client-side routes, or gets a CloudFront Function
scoped to the SPA behaviour. That is CHQ-003's decision and is named here so it is
not rediscovered.

### 6. The viewer `Host` header

Decided by the compute, and the two attempts that stripped it were right. Express
Mode's load balancer routes on a **host-header** listener rule
(<https://docs.aws.amazon.com/AmazonECS/latest/developerguide/express-service-work.html>,
"listener-configurations.rule-type: host-header"), so forwarding the viewer's
`Host` would arrive at a hostname the listener has no rule for and every API
request would fail at AWS's edge rather than in our code. The managed
`AllViewerExceptHostHeader` origin request policy is what `infra/cdn.tf` uses. The
one attempt that forwarded it was correct for the EC2 origin it had chosen, which
does not route on `Host` at all.

### 7. The CI stop condition

Decided: **`node tools/gates/ready.mjs`**, as one attempt proposed, rather than the
three Jest projects the other two listed. It is this repository's own stop
condition and already includes the three projects plus the type verdicts, the lint
lane and the lights; naming the projects individually would be a second, narrower
description of a gate that already exists.

## What this probe did NOT do

- **It did not test anything**, and neither has anything since. Every shape is a
  claim about services none of the attempts could reach: the account denies the
  compute by policy, and the `terraform` on this machine is v0.12.12 (October 2019)
  and cannot initialise a provider that has the resource at all.

  What HAS been verified of the written configuration is narrow and worth stating
  exactly: `terraform fmt -check -recursive infra/` is clean, so all of it is valid
  HCL2 in canonical form — established as a real verdict by planting both a
  formatting error (the file is named) and a syntax error (`Error: Invalid
  expression`, with the line) and watching that command fail on each. It proves
  nothing about whether an argument name exists in the provider, whether a type
  matches, or whether a reference resolves; that needs an initialised provider.
  `terraform validate` and a plan are the declared acceptance of CHQ-005 and are
  **owed** (TD-0019).
- **It did not decide that the arrangement works.** It decided what to build. The
  first `curl` against the live URL is the verdict, and until that exists every
  line of this record is a design, not a measurement.
- **It measured one vendor's tiers**, as the storage probe did. Three independent
  lineages would be a different and better measurement; this is not that.
- **It did not probe whether Beanstalk survives the `ec2` denial.** One attempt
  proposed a single `create-environment` call to find out. That question died with
  the choice above and is recorded in case the choice is revisited.
